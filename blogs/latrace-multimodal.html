    Building the Full-Modal Pipeline: LATRACE's Multimodal Memory Design

    ← Blogs

    April 2026  ·  LATRACE-AI on GitHub

    This post documents the technical work I did building the full-modal memory pipeline for OmniMemory (now open-sourced as LATRACE). LATRACE is a multimodal memory service for AI products that feeds text, audio, images, and video into a single temporal knowledge graph.

    Background: AI Memory's "Amnesia" Problem

    Most AI applications handle memory by stuffing the last few conversation turns into the context window and discarding anything that overflows. This is sufficient for short conversations, but as soon as a product needs long-term cross-session memory, the problem becomes apparent: a user's preferences expressed yesterday, a plan mentioned last week, a relationship established two months ago — all gone.

    The deeper problem is that modern products receive information across multiple modalities. Users send voice messages, share images, post videos. If memories from different modalities are managed in separate systems, it becomes very difficult to connect "what was said in yesterday's voice message" with "the context from today's text conversation."

    The core problem full-modal memory needs to solve is: get the memories from text, audio, and video into the same graph, accessible through the same retrieval interface, rather than forming isolated silos.

    Core Design: Why a Knowledge Graph Instead of a Vector Store

    The most common long-term memory approach is vector retrieval (RAG): slice historical conversations into chunks, vectorize them, and retrieve the top-k by similarity at query time. This works, but has clear limitations:

    • Cannot track state changes: if a user says "been really busy lately" today and "finally have some free time" next week, RAG will recall both fragments but has no notion of which state is current.
    • Cannot answer relational queries: "how has the relationship between Alice and Bob evolved?" — this type of question requires a graph structure, not similarity search.
    • Cannot perform temporal reasoning: "how long ago did she last mention this?" — RAG carries no temporal semantics.

    LATRACE's underlying storage is a TKG (Temporal Knowledge Graph). When a conversation, audio clip, or video comes in, it is not stored as a raw text chunk but compiled into graph nodes (entities, events, states) and time-annotated edges (relations, transitions).

    This allows the same API to simultaneously support:

    • Semantic retrieval (vector similarity, via Qdrant)
    • Structured queries (entity profiles, state changes, timelines, via Neo4j)
    • Evidence chain tracing (which conversation or video clip a given conclusion is based on)

    The Full-Modal Pipeline: How Three Modalities Enter the Same Graph

    LATRACE has three ingest endpoints, one per modality:

    POST /ingest/dialog/v1        # text conversation
POST /ingest/media/audio/v1  # audio
POST /ingest/media/video/v1  # video

    All three endpoints share the same output destination: they all land in the same TKG, sharing tenant_id, user_id, memory_domain, and temporal semantics. This is the key design principle of the full-modal pipeline — different modalities do not form independent memory systems; they operate under the same graph structure and the same retrieval contract.

    Text Pipeline

    Text conversation is the most basic entry point. The input is a set of conversation turns; the system then:

    1. Runs named entity recognition on the conversation content (people, places, events)
    2. Extracts relations and states between entities
    3. Writes to the TKG with the session_id and timestamp
    4. Simultaneously writes to the vector store (to support later semantic retrieval)

    Audio Pipeline

    The audio endpoint accepts an audio file or URL; the processing flow is:

    1. Transcription (ASR) produces text
    2. The text enters the same processing flow as the text pipeline, source-attributed
    3. Written to the TKG with source_type: audio and time offsets preserved

    This design means: "I'm going on a business trip to Shanghai next week" said in a voice message, and a later mention of "the Shanghai trip" in a text conversation, will be connected in the graph — and both are accessible through the same retrieval API.

    Video Pipeline

    Video is the most expensive of the three to process. The pipeline is:

    1. Frame extraction (keyframe sampling)
    2. Multimodal processing: visual understanding on frames, ASR on the audio track
    3. Both streams merged to extract time-aligned events and entities
    4. Written to the TKG with per-frame timestamps

    The work I was mainly involved in was on this pipeline: designing the ingest interface contract for audio and video (keeping the same isolation keys, temporal semantics, and async job pattern as the text endpoint), and extending the node types and edge types used when multimodal results are written to the TKG.

    Async Job Pattern

    All three ingest endpoints return a job_id immediately rather than waiting for the write to complete. Clients poll GET /ingest/jobs/{job_id} to check processing status (PENDING → PROCESSING → COMPLETED / FAILED).

    This design is appropriate: audio and video processing (transcription, frame extraction, entity extraction) takes an unpredictable amount of time, and blocking the caller to wait for completion is impractical. The async job pattern also supports retry from failure — if a step fails, it can be re-triggered from that point rather than re-running the entire pipeline.

    Two Integration Modes

    LATRACE's retrieval interface can be used in two ways:

    Mode A (Retrieval API): call POST /retrieval/dialog/v2 directly, pass a query, receive memory fragments and an evidence summary, then manually compose them into a prompt. This is the fastest integration path — just 2 HTTP calls.

    Mode B (ADK Tools): expose memory as a set of tools the agent can call: entity_profile (query an entity profile), entity_status (query current state), status_changes (query state change history), topic_timeline (query a timeline), relations (query the relation graph), and more. The agent actively issues memory queries as needed rather than having all possibly-relevant context pre-stuffed into the prompt.

    Both modes run on the same underlying memory service; the difference is who decides what to retrieve — in Mode A the developer writes the query explicitly, in Mode B the agent issues tool calls autonomously at runtime.

    Multi-Tenant Isolation

    All ingest and retrieval requests carry an X-Tenant-ID header, combined with user_id and memory_domain in the payload, forming a three-level isolation key. These three keys are first-class citizens in the TKG — every node and edge in the graph carries them, and filtering happens at the storage layer rather than being enforced in application code after the fact.

    This matters in a SaaS product: multiple tenants share a single memory service, but each tenant's memory data is strictly isolated at the storage layer, without relying on application-level correctness to ensure security.

    A Design Detail: Schema Consistency

    The hardest part of the full-modal pipeline is not transcription or frame extraction — it is schema consistency when different modalities write to the TKG. A text conversation that says "Alice has been under increasing stress lately" and a video that identifies tense facial expressions and voice tone changes for Alice should use the same node types (Person, EmotionalState) and edge types (hasStatus, changedAt) in the graph, regardless of where the information came from.

    Once schema consistency breaks down, "unified retrieval across all modalities" becomes meaningless — you cannot traverse a graph across different node types. LATRACE enforces a shared core schema for all modalities by design; differences appear only in the source field and do not affect the graph structure itself.

    This is what I consider the most critical architectural judgment in the full-modal pipeline design: modality differences are absorbed at ingest time and do not propagate into the storage layer.
