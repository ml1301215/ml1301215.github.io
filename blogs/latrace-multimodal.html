    全模态链路的搭建：LATRACE 的多模态记忆设计

    ← Blogs

    April 2026  ·  LATRACE-AI on GitHub

    这篇文章记录了我参与 OmniMemory（现已开源为 LATRACE）全模态记忆链路搭建的技术过程。LATRACE 是一个面向 AI 产品的多模态记忆服务，把文本、音频、图像和视频统一接入同一张带时间语义的知识图谱。

    背景：AI 记忆的"失忆症"

    大多数 AI 应用的记忆方案是：把最近几轮对话塞进上下文窗口，超出窗口就丢掉。这在短对话里够用，但一旦产品需要跨会话的长期记忆，问题就出现了：用户昨天说过的偏好、上周提到的计划、两个月前建立的人物关系，全部消失。

    更深的问题在于：现代产品里，信息不只来自文本。用户会发语音消息、分享图片、发视频。如果把这些模态的记忆分散在不同系统里管理，检索时就很难把"昨天那段语音里提到的事"和"今天文字对话里的上下文"关联起来。

    全模态记忆要解决的核心问题是：让文本、音频、视频的记忆进入同一张图，用同一套检索接口访问，而不是形成彼此割裂的孤岛。

    设计核心：为什么用图谱而不是向量库

    最常见的长期记忆方案是向量检索（RAG）：把历史对话切成块，向量化后存起来，查询时按相似度召回 top-k 片段。这个方案有效，但有明显的局限：

    • 无法追踪状态变化：用户今天说"最近很忙"，下周说"终于闲下来了"，RAG 会把这两段都召回，但不知道哪个是更新的状态。
    • 无法回答关系型问题："Alice 和 Bob 之间的关系怎么变化的？"这类问题需要图结构，不是相似度检索。
    • 无法做时间推理："她上次提到这件事是多久前？"RAG 没有时间语义。

    LATRACE 的底层是 TKG（Temporal Knowledge Graph，带时间语义的知识图谱）。对话、音频、视频进来之后，不是直接存成文本块，而是被编译成图节点（实体、事件、状态）和带时间标注的边（关系、变化）。

    这样，同一个 API 可以同时支持：

    • 语义检索（向量相似度，用 Qdrant）
    • 结构化查询（实体档案、状态变化、时间线，用 Neo4j）
    • 证据链追溯（某个结论基于哪条对话/哪段视频）

    全模态链路：三种模态如何进入同一张图

    LATRACE 有三条 ingest 入口，分别对应三种模态：

    POST /ingest/dialog/v1   # 文本对话
POST /ingest/media/audio/v1  # 音频
POST /ingest/media/video/v1  # 视频

    三条入口的 出口是统一的：都会落到同一张 TKG 里，共享 tenant_id、user_id、memory_domain 和时间语义。这是全模态链路设计的关键点——不同模态不形成独立的记忆系统，而是在同一套图结构和同一套检索契约下工作。

    文本链路

    文本对话是最基础的入口。输入是对话的 turns（轮次），系统会：

    1. 把对话内容做实体识别（人物、地点、事件）
    2. 提取实体间的关系和状态
    3. 写入 TKG，附带 session_id 和时间戳
    4. 同时写入向量库（支持后续的语义检索）

    音频链路

    音频入口接收音频文件或 URL，处理流程是：

    1. 转录（ASR）得到文本
    2. 以 source-based 方式进入和文本相同的处理流程
    3. 写入 TKG 时保留 source 来源（source_type: audio）和时间偏移量

    这个设计意味着：一段语音里说的"我下周要去上海出差"，和文字对话里后来提到的"上海出差"，会在图谱里被连接起来，并且都可以用同一套检索 API 访问。

    视频链路

    视频是三者中处理成本最高的。链路是：

    1. 视频分帧（关键帧提取）
    2. 多模态处理：帧图像做视觉理解，音轨做 ASR
    3. 两路结果合并，提取时间对齐的事件和实体
    4. 写入 TKG，带帧时间戳

    我参与的工作主要集中在这条链路：设计音频和视频的 ingest 接口契约（和文本入口保持一致的隔离键、时间语义和异步作业模式），以及多模态结果进入 TKG 时的节点类型和边类型的扩展。

    异步作业模式

    三条 ingest 入口都返回一个 job_id，不是立即返回写入结果。客户端需要轮询 GET /ingest/jobs/{job_id} 来确认处理状态（PENDING → PROCESSING → COMPLETED / FAILED）。

    这个设计是合理的：音频和视频的处理（转录、分帧、实体提取）耗时不可控，同步等待会阻塞调用方。异步作业还支持断点重试——如果某个步骤失败，可以从失败点重新触发，而不是重跑整条链路。

    两种接入模式的选择

    LATRACE 的检索接口有两种用法：

    模式 A（Retrieval API）：直接调用 POST /retrieval/dialog/v2，传入查询，得到记忆片段和证据摘要，再手动拼进 prompt。这是最快的接入方式，2 个 HTTP 调用即可。

    模式 B（ADK Tools）：把记忆暴露成 Agent 可调用的工具集：entity_profile（查实体档案）、entity_status（查当前状态）、status_changes（查状态变化历史）、topic_timeline（查时间线）、relations（查关系图）等。Agent 按需主动发起记忆查询，而不是把所有可能相关的上下文都塞进 prompt。

    两种模式跑在同一套记忆服务之上，差别在于谁来决定"查什么记忆"：模式 A 是开发者手动写查询，模式 B 是 Agent 在运行时自主发起工具调用。

    多租户隔离

    所有 ingest 和 retrieval 请求都带 X-Tenant-ID header，加上 payload 里的 user_id 和 memory_domain，构成三级隔离键。这三个键在 TKG 里是第一公民——图谱里的每个节点和边都携带这些键，查询时在存储层就做过滤，不是在应用层事后剔除。

    这在 SaaS 产品里很重要：多个租户共用一套记忆服务，但彼此的记忆数据在存储层就严格隔离，不依赖应用代码的正确性来保证安全性。

    一个设计细节：schema 一致性

    全模态链路最难处理的部分不是转录或分帧，而是不同模态写入 TKG 时的 schema 一致性。文本对话里说"Alice 的压力最近在上升"，和视频里识别出 Alice 表情紧张、语音语调变化，这两件事在图谱里应该用同一套节点类型（Person、EmotionalState）和边类型（hasStatus、changedAt），而不是因为来源不同就用不同的 schema。

    一旦 schema 不一致，"把三种模态的记忆统一查询"就变成空话——你无法跨越不同的节点类型做图遍历。LATRACE 在设计上强制要求所有模态共享核心 schema，差异只存在于 source 字段里，而不影响图结构本身。

    这是我在参与全模态链路设计时认为最关键的一个判断：模态的差异在 ingest 阶段消化，不带入存储层。
