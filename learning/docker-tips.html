    Docker Usage Notes

    ← Learning

    Compiled from experience deploying services and training jobs with Docker during internships at JD.com and Chaitin Tech. Docker's concepts are straightforward; the difficulty is in the details.

    1. The Difference Between Images and Containers (A Common Misconception)

    An image is a static template; a container is a running instance. One image can launch multiple containers.

    The most common misconception: modifying a file inside a container and expecting it to persist on the next start. In reality, a container's filesystem is a writable layer separate from the image; once the container is deleted, that layer disappears. To persist data, you must use a volume or bind mount.

    2. Image Layers and Build Cache

    Each instruction in a Dockerfile (RUN, COPY, ADD) creates a new image layer. During a build, if a layer's content is unchanged, Docker reuses the cached layer and skips re-executing it and all subsequent layers — provided all preceding layers also hit the cache.

    This means instruction order matters. Put rarely-changing instructions first and frequently-changing ones last to maximize cache hits.

    # Inefficient: reinstalls dependencies on every code change
FROM python:3.10
COPY . /app
RUN pip install -r /app/requirements.txt

# Efficient: copy dependency file first, then copy code
FROM python:3.10
COPY requirements.txt /app/requirements.txt
RUN pip install -r /app/requirements.txt
COPY . /app

    With the second approach, as long as requirements.txt is unchanged, the pip install layer hits the cache, saving substantial build time.

    3. Data Persistence: Volumes vs Bind Mounts

    Both approaches mount host data into the container; the difference is in how they are managed:

    • bind mount: mounts a specific host path into the container. Intuitive and suitable for development (code changes sync in real time).
      docker run -v /host/path:/container/path ...
    • volume: an independent storage area managed by Docker, independent of the host directory structure. Suitable for production environments and persistent data.
      docker run -v my-volume:/container/path ...

    For training jobs, use bind mounts for model weights and datasets so the data remains on the host even after the container is deleted.

    4. Do Not Run as Root

    By default, processes inside a container run as root. If the container is compromised, root privileges could be exploited to escape to the host. Even for internal services, it is good practice to create a non-root user in the Dockerfile:

    RUN useradd -m appuser
USER appuser

    This is especially important for services that expose external interfaces.

    5. Do Not Bake Secrets into Image Layers

    Every layer in a Dockerfile is permanently stored. Even if you delete a file with a later RUN rm, that file still exists in the earlier layer and is visible via docker history.

    # Wrong: API key baked into an image layer
ENV API_KEY=my-secret-key

# Correct: pass it as an environment variable at runtime
docker run -e API_KEY=my-secret-key ...

    For cases where a secret is needed during the build (e.g., pip-installing a private package), use Docker BuildKit's --secret flag; the secret will not be included in any image layer.

    6. Dealing with Oversized Images

    Oversized images (common causes: apt-get cache not cleaned, pip cache, temporary files) result in slow pulls and high storage usage.

    # Clean apt cache (must be in the same RUN block to avoid persisting in an intermediate layer)
RUN apt-get update && apt-get install -y git curl \
    && rm -rf /var/lib/apt/lists/*

# Clean pip cache
RUN pip install --no-cache-dir -r requirements.txt

    Another option is a multi-stage build: use a large image for compilation, then copy only the build artifacts into a small final image. Not commonly needed for pure-Python projects, but very effective for projects with C extensions or compiled binaries.

    7. Additional Configuration for GPU Training

    Containers cannot see GPUs by default. You need to install nvidia-container-toolkit and pass a flag at runtime:

    # Install nvidia-container-toolkit (one-time setup on the host)
# Reference: https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/install-guide.html

# Mount all GPUs at runtime
docker run --gpus all ...

# Mount only GPU 0
docker run --gpus '"device=0"' ...

    Run nvidia-smi inside the container to verify the GPU is visible.

    8. Quick Reference: Common Commands

    docker ps -a                    # list all containers (including stopped)
docker images                   # list local images
docker rm $(docker ps -aq)      # remove all stopped containers
docker rmi $(docker images -q)  # remove all images (use with caution)
docker logs -f container_id     # follow container logs in real time
docker exec -it container_id bash  # open a shell in a running container
docker build -t my-image:v1 .   # build an image
docker system prune             # clean up unused images, containers, networks
