    LLM Fine-Tuning Notes: QLoRA + GRPO

    ← Learning

    These notes are compiled from fine-tuning Qwen3-30B-A3B for security alert classification during my internship at Chaitin Tech (October–December 2025). The task: automatically sort alerts received by an enterprise SOC into five severity levels — critical / high / medium / low / informational — to help analysts triage. The training run uses QLoRA to fit the model in GPU memory, GRPO to align classification behavior, and finishes on a dual-A100 setup.

    1. Problem Background: Why a General LLM Isn't Enough

    General-purpose LLMs (Qwen3, LLaMA, GPT-4) are pretrained on huge amounts of internet text and have broad language ability. But in a specialized setting like an enterprise security operations center (SOC), using them off the shelf works poorly. The reason isn't that the model "doesn't know" security — most mainstream models have some grasp of CVEs, the MITRE ATT&CK framework, and common attack techniques. The problem is distribution mismatch: the model has never seen this company's alert format, log field naming conventions, business context, or its specific definition of asset importance.

    A second issue is asymmetric loss. In typical classification tasks, false positives and false negatives carry roughly the same cost, so overall accuracy is a reasonable optimization target. In a SOC:

    • Missing a critical/high alert (false negative): the attacker can persist in the network for a long time, exfiltrate data, or deploy ransomware. The downstream cost is severe and remediation is expensive.
    • Wrongly flagging an alert as critical/high (false positive): analysts get alert fatigue and slow down, but no actual security incident happens. The damage is much smaller than a missed critical.

    Because of this asymmetry, even a model with a respectable overall F1 is unusable in production if its critical-alert recall is too low. Standard supervised fine-tuning (SFT) maximizes log-likelihood and treats every error the same, so it can't naturally encode an asymmetric loss. That gives us two requirements:

    1. Domain adaptation: teach the model the company's alert format and field semantics — a distribution-alignment problem.
    2. Reward alignment: train the model to actually pursue the business objective (don't miss severe alerts), not just fit the labeled distribution — a loss-function design problem.

    QLoRA addresses the first (efficient domain adaptation), GRPO the second (reward alignment). The combination is the reason this technical approach was chosen.

    Task definition: input is an alert produced by enterprise firewalls, IDS, EDR, or SIEM systems (alert title, source/destination IP, port, protocol, raw log snippet, device type, and so on). Output is one of five severity levels: critical (respond immediately), high (respond same day), medium (respond this week), low (schedule for next week), informational (record only, no response needed). Alerts are labeled retrospectively by SOC analysts. The dataset has roughly 12,000 samples, with critical at 4%, high at 11%, and the remaining three classes at 20–30% each — a typical "rare severe class" distribution.

    2. LoRA: Low-Rank Decomposition of Weight Updates

    To understand QLoRA you first need LoRA (Low-Rank Adaptation). The idea: during fine-tuning, the weight update ΔW has low intrinsic rank, so it can be approximated by the product of two small matrices, cutting trainable-parameter count substantially.

    Memory bottleneck for full fine-tuning: Qwen3-30B-A3B has about 30 billion parameters. Full fine-tuning needs: model weights (fp16, ~60 GB) + gradients (same size, ~60 GB) + Adam optimizer state (first- and second-order moments, ~120 GB) ≈ 240 GB. Far beyond what's practical on a single multi-GPU node, and not feasible in most industrial settings.

    The math of LoRA: instead of updating the original weight matrix W ∈ ℝd×k directly, LoRA constrains the update ΔW to be a product of two low-rank matrices:

    W' = W + ΔW = W + A · B
    A ∈ ℝd×r,   B ∈ ℝr×k,   r << min(d, k)

    The forward pass becomes h = W·x + (A·B)·x × (α/r), where α is a scaling hyperparameter. During training W is frozen (no gradient flows through it) and only A and B are updated. At inference time ΔW = A·B can be merged back into W, so inference speed matches the original model — no extra inference overhead.

    Parameter count comparison (using a Qwen3-30B attention projection layer with d=k=4096, r=8):

    • Full fine-tuning of this layer: 4096 × 4096 = 16,777,216 parameters
    • LoRA (r=8) for this layer: 8 × (4096 + 4096) = 65,536 parameters
    • Compression ratio about 256:1; total trainable parameters end up at roughly 0.14% of the base model

    Why low-rank decomposition works: Aghajanyan et al. (2020) showed empirically that pretrained language models have a low "intrinsic dimension" — in the high-dimensional parameter space, useful optimization directions concentrate in a subspace much smaller than the full dimension. Weight updates during fine-tuning inherit this property: the bulk of task-relevant updates fall in a low-rank subspace, and the higher-rank components are mostly noise. So low-rank decomposition loses very little useful information while shrinking parameter count substantially.

    Initialization: A is initialized with random Gaussian values, B is initialized to zero. This gives ΔW = A·B = 0 at the start of training, so LoRA begins from the base model's behavior and avoids early-training instability from random perturbation.

    # LoRA adds two small matrices A and B alongside the frozen weight W
# Forward pass: h = W·x + (A·B)·x * (alpha/r)
# Only A and B are updated during training; W remains frozen

from peft import LoraConfig

lora_config = LoraConfig(
    r=8,                # rank r: controls LoRA expressiveness
                        # Common choices: 4, 8, 16, 32
                        # r=8 is a safe starting point
                        # Increase to r=16 if the model underfits on your task
                        # Memory scales linearly with r: r*(d+k) params per layer
    lora_alpha=16,      # scaling factor applied as alpha/r in the forward pass
                        # Rule of thumb: set to 2*r initially (here 2*8=16)
                        # Higher alpha = stronger LoRA influence over base weights
                        # Can tune: lower if LoRA is overwhelming base knowledge
    target_modules=[
        "q_proj", "k_proj", "v_proj", "o_proj",   # self-attention projections
        "gate_proj", "up_proj", "down_proj",        # MLP (FFN) projections
        # Including all 7 module types gives best coverage for Qwen architecture
        # For simpler tasks, attention-only (first 4) sometimes sufficient
        # FFN projections are important for knowledge/classification tasks
    ],
    lora_dropout=0.05,  # dropout applied to LoRA layers for regularization
                        # 0.05 provides mild regularization
                        # Set to 0 when using unsloth (custom kernel assumes no dropout)
    bias="none",        # whether to train bias terms alongside LoRA weights
                        # "none": don't train biases (most common, safest)
                        # "all": train all biases (marginal gain, more params)
                        # "lora_only": train biases only in LoRA layers
    task_type="CAUSAL_LM",  # task type for PEFT model wrapping
                             # CAUSAL_LM = decoder-only autoregressive model
)

    Which modules to attach LoRA to: cover the projection matrices that hold the bulk of the parameters and matter most for the task. For most Transformer decoders (Qwen, LLaMA, Mistral), it's reasonable to cover all attention projections (q/k/v/o) and FFN projections (gate/up/down). For pure classification or format-transfer tasks, attention layers alone are sometimes enough; for tasks that need to change the model's knowledge or reasoning style, FFN layers shouldn't be skipped.

    3. QLoRA: 4-bit Quantization + LoRA

    QLoRA (Quantized LoRA, Dettmers et al. 2023) adds 4-bit quantization on top of LoRA, taking the model's storage footprint from 2 bytes per parameter (fp16) down to about 0.5 bytes per parameter. For a 30B-parameter model:

    • fp16 storage: 30B × 2 bytes = 60 GB
    • 4-bit quantized storage: 30B × 0.5 bytes = 15 GB
    • Roughly 75% saved, so a single A100 (80 GB) can hold the base model + LoRA adapter + optimizer state

    NF4 (NormalFloat4) quantization: QLoRA uses NF4 instead of plain INT4. The reason: after pretraining, neural-network weights are approximately zero-mean Gaussian. NF4 places non-uniform quantization buckets so each 4-bit value lands on a quantile of that distribution. In information-theoretic terms it's the optimal 4-bit quantization for normally distributed weights, and it loses less precision than uniform quantization.

    Double quantization: quantization itself produces quantization constants (one scaling factor per block), usually stored in fp32. Double quantization quantizes those constants too (fp32 → fp8 or fp4), saving more memory. For a 30B model this gives about 3–4 GB of additional savings.

    Paged optimizers: during GRPO training, optimizer state (Adam first/second moments, each trainable_params × 4 bytes) can spike GPU memory at certain steps. The paged optimizer (paged_adamw_32bit) uses NVIDIA unified memory to offload optimizer state to CPU RAM when GPU memory is tight, avoiding OOM at the cost of occasional CPU–GPU transfer latency.

    Storage precision is separate from compute precision: quantization only affects how weights are stored. Matrix multiplications dequantize weights to bf16 or fp16 before computing, so numerical precision in the math is preserved. The trade-off is "approximate storage, accurate computation" — storage savings are large, compute precision loss is small.

    import torch

    The cost of QLoRA: 4-bit quantization introduces a small quantization error. On classification tasks, our experiments showed the QLoRA (4-bit) F1 was within 1pp of fp16 LoRA — small enough to ignore in practice. The effect on generation tasks (summarization, dialogue) may be slightly larger, but for discriminative classification tasks it's barely visible.

    4. Comparing SFT, DPO, PPO, and GRPO

    Before deciding on GRPO we walked through the four mainstream alignment / fine-tuning methods. Each is designed around a different training signal and use case; understanding their trade-offs helps pick the right one.

    SFT (Supervised Fine-Tuning): the basic approach. Given a batch of (input, correct output) pairs, maximize the model's log-likelihood on the correct output. Pros: simple to implement, fast to converge, the data format is intuitive. Cons: the objective is decoupled from the business metric — SFT optimizes "how literally the output matches the labeled text," not "is the classification correct." More importantly, SFT can't encode asymmetric loss: it treats misclassifying critical as informational the same as misclassifying medium as low, even though the real cost is very different. SFT also only fits the training distribution, which limits its help on critical, where labels are sparse.

    DPO (Direct Preference Optimization): uses preference pairs (chosen better than rejected) and avoids training a separate reward model. Compared with PPO, DPO is more stable and simpler. Cons: needs paired labels (a "good answer" and a "bad answer" for the same input), which costs more to produce; preference-pair quality drives the result; and it's hard to encode a continuous, asymmetric reward signal — DPO knows A is better than B but not by how much, and can't easily express "this kind of error is six times worse than that one."

    PPO (Proximal Policy Optimization): full reinforcement learning. Has a Policy network (the LLM being trained), a Reward model (scorer), and a Critic/Value network (baseline estimator). The most flexible — it can encode any reward signal. Cons: needs two large models in memory at once (Policy + Critic), more than 2× the GPU memory of a single model; the Value network is unstable and prone to reward hacking; many hyperparameters, hard to tune; for a 30B model, full PPO is essentially impossible on a dual-A100 setup.

    GRPO (Group Relative Policy Optimization): a PPO variant designed for LLM fine-tuning, introduced by the DeepSeek team. The trick: replace the Critic-network baseline with a group-relative reward normalization — for each prompt, generate G candidates, subtract the group mean from each candidate's reward and divide by the group standard deviation to get a normalized advantage. This eliminates the Value network entirely, cutting memory roughly in half and improving training stability.

    Reasons we picked GRPO:

    • No paired labels needed — a single labeled alert is enough to define a reward
    • A custom reward function can encode asymmetric loss directly, no approximation
    • No Critic, so a 30B-class model fits on dual A100s
    • Group normalization makes the reward scale self-adaptive, so we don't have to calibrate absolute reward values
    • The TRL library (Hugging Face) has a production-ready GRPOTrainer, low integration cost
    Method Data needed Memory Custom reward Stability Use case
    SFT (input, output) pairs Low No High Format transfer, initial alignment
    DPO Preference pairs Medium Indirect High Dialogue alignment with quality preference pairs
    PPO Reward-labeled samples Very high (2×) Full Low Complex reward + abundant resources
    GRPO Reward-labeled samples Medium (no Critic) Full Medium-high Custom reward + limited resources

    5. How GRPO Works

    The idea behind GRPO is to replace the Critic-network baseline with a group-relative comparison, keeping the alignment power of RL while cutting compute substantially.

    The baseline problem in standard PPO: policy-gradient methods update parameters to maximize expected reward E[r(y|x)]. Using raw rewards as the gradient signal has very high variance (rewards on different prompts have different scales and aren't directly comparable), so PPO introduces a Value network V(x) as a baseline, replacing the gradient signal with the advantage A(y,x) = r(y,x) − V(x). But training V(x) requires a network at the same scale as the Policy, which is expensive.

    GRPO's advantage estimate: for each prompt x, sample G candidate responses {y1, ..., yG}, score them to get rewards {r1, ..., rG}, and normalize within the group:

    Âi = (ri − mean(r1, ..., rG)) / std(r1, ..., rG)

    The group mean is the adaptive baseline; the group standard deviation is the normalization factor. So Âi means "in the G candidates for the same prompt, how much better than average is candidate i, in standard-deviation units."

    Policy update objective: as in PPO, use a clipped surrogate objective to prevent overly large policy updates:

    LGRPO(θ) = E[ min( rt(θ) ċ Âi,  clip(rt(θ), 1−ε, 1+ε) ċ Âi ) ]

    where rt(θ) = πθ(yi|x) / πold(yi|x) is the new-vs-old policy probability ratio, and ε is the clipping range (usually 0.1–0.2), keeping the policy from moving too far in a single step.

    Why group normalization is a valid baseline: the Critic network's role is to estimate "for prompt x, what's the average expected reward?" so it can serve as a comparison baseline. For G responses generated from the same prompt x, all the prompt-related context is shared — only the responses themselves differ in quality, and that's what causes reward differences. The group mean naturally approximates V(x), with no training needed, just sampling. Larger G gives a more accurate approximation and lower gradient variance, but compute cost grows linearly with G.

    KL regularization: to prevent the policy from drifting too far from the reference model (the original base), GRPO usually adds a KL penalty: L = LGRPO − β · KL(πθ || πref), where β controls regularization strength. This stops the model from finding degenerate behaviors that chase the reward (for example, producing a fixed phrase to lock in a format reward at the cost of language ability).

    Compute graph for one GRPO step:

    1. Sample a batch of prompts {x1, ..., xB} from the training set
    2. For each prompt, generate G candidate responses with the current policy (B×G sequences total)
    3. Call the Reward function on all B×G responses to get a reward matrix R ∈ ℝB×G
    4. Normalize row-wise (each prompt independently) to get the advantage matrix Â
    5. Take one gradient step on the policy using the clipped surrogate loss
    6. Update the reference probabilities (old policy), ready for the next step

    6. Reward Function Design

    Reward function design is where the key decisions in GRPO fine-tuning happen. It encodes human knowledge about what counts as a good output, and shapes the model's final behavior. Design principles:

    1. Encode domain knowledge: the reward should reflect the real evaluation criterion of the task, not a proxy (such as output length).
    2. Handle asymmetric cost explicitly: when error types have very different costs, the reward differences should be roughly proportional to the cost differences.
    3. Defensive parsing: model output is natural language with all kinds of format variations. The reward function has to reliably extract the key information from the output, rather than dropping every malformed sample to the floor reward.
    4. Calibrate reward magnitude: rewards that are too large or too small both cause gradient problems. A common range: +1.0 for correct, and -0.5 to -3.0 for errors of varying severity.

    Asymmetric cost matrix for security alert classification:

    Error type Example Real cost Reward
    Correct critical → critical None +1.0
    Severe underestimate (2+ levels) critical → medium/low/info Very high (severe threat missed) -3.0
    Mild underestimate (1 level) critical → high, high → medium High (priority lowered) -1.5
    Severe overestimate (2+ levels) info → high/critical Low (extra noise) -0.5
    Adjacent error (1 level) medium → high, low → medium Low (acceptable drift) -0.8
    Format error Output cannot be parsed Medium (unusable) -1.0

    7. Full Training Configuration

    This is the configuration we settled on after about 20 iterations of experiments. Each hyperparameter has a rationale and a tuning suggestion.

                                            "eval":  "alerts_eval.jsonl"})

# ── GRPO training configuration ───────────────────────────────────────────────
grpo_config = GRPOConfig(
    # ── GRPO-specific ──────────────────────────────────────────────────────────
    num_generations=8,      # G: group size; number of completions per prompt
                             # Higher G = better gradient estimates (lower variance)
                             # but G× more GPU memory during generation phase
                             # G=8 is a good default; G=4 if memory-constrained
                             # G=16 gave marginal improvement but required halving batch size
    max_new_tokens=128,      # max response length; 128 is generous for single-word output
                             # important to not cut off thinking tokens if using CoT
    temperature=0.9,         # sampling temperature for generating G candidates
                             # higher temp → more diverse candidates → better gradient signal
                             # too high → incoherent outputs that all get bad rewards
    top_p=0.95,              # nucleus sampling; standard value

    # ── Optimization ──────────────────────────────────────────────────────────
    learning_rate=5e-6,             # low LR critical for RL stability
                                     # SFT typically uses 1e-4 to 2e-4; RL is noisier
                                     # policy gradient updates are high-variance;
                                     # too-high LR causes reward collapse
    num_train_epochs=3,
    per_device_train_batch_size=2,  # number of prompts per GPU per step
                                     # with G=8, each step processes 2×8=16 sequences
                                     # set to 1 if OOM
    gradient_accumulation_steps=4, # effective batch = 2 prompts × 4 accum × 8 gen = 64 samples
                                     # accumulation lets you maintain effective batch size
                                     # while keeping instantaneous memory low
    warmup_ratio=0.1,               # 10% of total steps as warmup
                                     # essential for RL: without warmup, early large
                                     # gradients can permanently damage the policy
    weight_decay=0.01,              # mild L2 regularization

    # ── Memory optimization ────────────────────────────────────────────────────
    gradient_checkpointing=True,    # recompute activations during backward pass
                                     # reduces activation memory by ~8-10x at cost of
                                     # ~30% extra compute; mandatory for 30B+ models
    bf16=True,                       # use bfloat16 for training compute
                                     # preferred over fp16 on Ampere+ (A100, H100)
    optim="paged_adamw_32bit",      # paged optimizer: offloads optimizer states to CPU
                                     # when GPU memory is tight, prevents OOM spikes
                                     # "32bit" refers to optimizer state precision,
                                     # not model weights

    # ── KL regularization ─────────────────────────────────────────────────────
    kl_coef=0.01,                   # KL penalty coefficient (beta in the GRPO paper)
                                     # prevents policy from drifting too far from base model
                                     # increase if observing reward hacking or mode collapse
                                     # decrease if policy updates are too conservative

    Metrics to watch during training:

    • reward/mean: group-mean reward. Should rise early in training and then plateau (typically around 0.5–0.8). If it keeps dropping or oscillates wildly, check learning_rate and kl_coef.
    • reward/std: group reward standard deviation. Should stay non-zero. If it approaches zero, all generations have collapsed to the same output and the gradient signal disappears — try raising temperature.
    • kl: KL divergence to the reference model. Should rise slowly and stabilize in a reasonable range (0.1–1.0). If it spikes, raise kl_coef.
    • policy_loss: policy loss. Should decline slowly and stabilize.

    8. unsloth Acceleration

    unsloth is an acceleration library tailored to QLoRA / LoRA training, using hand-written CUDA kernels and an optimized Flash Attention implementation. On A100 it typically gives about 2× speedup (the project reports 1.5–2.5× across various benchmarks). It's API-compatible with transformers + peft, so it's roughly a drop-in replacement and the training code barely changes.

    What unsloth optimizes:

    • Hand-written LoRA CUDA kernel: standard PEFT implements LoRA forward/backward at the PyTorch level, with extra Python overhead and kernel launch cost. unsloth fuses A·B with the base W matmul into a single CUDA kernel, cutting memory round-trips.
    • Flash Attention 2 integration: automatic Flash Attention 2 with tiled compute, reducing attention's memory footprint from O(n²) to O(n) — important on long-sequence training.
    • Custom gradient checkpointing: unsloth's gradient checkpointing is more aggressive than transformers' default, with re-computation granularity tuned for LoRA, avoiding unneeded recomputation.
    from unsloth import FastLanguageModel

# ── Drop-in replacement for from_pretrained + get_peft_model ──────────────────
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="Qwen/Qwen3-30B-A3B",
    max_seq_length=2048,    # maximum sequence length; affects memory allocation
                             # set to actual max(input + output) in your dataset
    dtype=None,              # None = auto-detect
                             # will use bfloat16 on Ampere+ (A100, RTX 3090+)
                             # falls back to float16 on older GPUs
    load_in_4bit=True,       # enable 4-bit NF4 quantization (same as BitsAndBytes)
)

# ── Apply LoRA with unsloth-specific settings ──────────────────────────────────
model = FastLanguageModel.get_peft_model(
    model,
    r=8,
    target_modules=[
        "q_proj", "k_proj", "v_proj", "o_proj",
        "gate_proj", "up_proj", "down_proj",
    ],
    lora_alpha=16,
    lora_dropout=0,                         # IMPORTANT: must be 0 with unsloth
                                             # unsloth's custom kernel does not support
                                             # dropout in the LoRA computation path
                                             # (standard peft: set to 0.05)
    bias="none",
    use_gradient_checkpointing="unsloth",   # use unsloth's custom gradient checkpointing
                                             # more memory-efficient than standard
                                             # "True" also works but is slower
    random_state=42,
    use_rslora=False,       # RSLoRA: rank-stabilized LoRA (scales by 1/sqrt(r))
                             # useful when r is large (>=32); off by default
    loftq_config=None,      # LoFTQ: quantization-aware LoRA initialization
                             # can improve convergence on highly quantized models
                             # set to LoftQConfig() if NF4 precision is insufficient
)

# The rest of training is identical to standard TRL GRPOTrainer
# No other code changes needed — this is the full unsloth integration

    Factor unsloth standard peft
    Speed first Yes, ~2× speedup
    Custom training loop More flexible
    Need dropout in LoRA Supported
    Non-standard architectures May not be supported More general
    Production stability Active maintenance, large community HuggingFace official
    Debuggability Harder (custom kernels) Standard PyTorch, easy

    What we actually did: started with standard PEFT to debug the training logic and confirm the reward function and hyperparameters, then switched to unsloth for the full run to save time. The two code bases are nearly interchangeable.

    9. Hyperparameter Tuning Guide

    A walkthrough of each major hyperparameter — what it controls, the typical range, and rules of thumb from our experiments.

    LoRA architecture parameters

    r (rank): controls LoRA's expressive capacity. Larger r means more learnable update dimensions, with trainable parameter count growing as O(r) (specifically r×(d+k) per layer).

    • Typical range: 4, 8, 16, 32 (above 64 usually shows no further gain)
    • Starting point: r=8. If training loss converges quickly but validation underfits, raise to r=16 or r=32
    • For very simple tasks (format conversion), r=4 is enough; for tasks that need to substantially change the model's knowledge or reasoning, consider r=32
    • Larger r isn't always better — beyond a threshold, performance flattens while memory keeps growing

    lora_alpha (scaling factor): controls LoRA's effective influence on the base weights. The forward-pass scaling is alpha/r.

    • Starting point: 2×r (e.g., r=8 → alpha=16)
    • If LoRA isn't having enough effect (model behavior barely changes), raise alpha or lower r
    • If training is unstable (loss oscillates), lower alpha or raise r (smaller scaling ratio)
    • RSLoRA (use_rslora=True) changes scaling to alpha/sqrt(r), more stable for large r

    target_modules: which weight matrices LoRA attaches to.

    • Maximum coverage (recommended): attention projections (q/k/v/o) + FFN projections (gate/up/down), 7 modules in total
    • Minimum coverage: q_proj + v_proj only (fewest parameters, for memory-tight setups)
    • Rule of thumb: classification and knowledge-heavy tasks need FFN layers; pure format-transfer tasks may get away with attention-only

    GRPO training parameters

    learning_rate: among the more sensitive hyperparameters in RL fine-tuning.

    • SFT typical range: 1e-4 to 2e-4
    • GRPO recommended range: 1e-6 to 1e-5 (1–2 orders of magnitude lower than SFT)
    • Why: policy-gradient updates are noisy, and a high LR causes the policy to oscillate and produce "reward collapse" — the model finds a degenerate strategy that locks in a stable reward instead of learning real classification
    • Starting point: 5e-6; if the reward curve oscillates a lot, drop to 2e-6; if reward rises too slowly, raise to 1e-5

    num_generations (G): candidates generated per prompt.

    • Typical range: 4 to 16
    • G=8 was our best balance in experiments — good gradient quality with reasonable memory and speed
    • G=4: trains faster, but the advantage estimate is noisier and convergence takes more epochs
    • G=16: more accurate gradients, but you have to drop per_device_train_batch_size to 1
    • Memory impact: all G candidates live in memory during generation, so each +1 in G costs about as much as +1 in batch

    gradient_checkpointing: trade activation memory for compute time.

    • Required for 30B+ models; optional below 20B (turning it on lets you raise batch size or sequence length)
    • Typical cost: about 30% more compute, in exchange for roughly 8–10× less activation memory
    • With unsloth: set to "unsloth" rather than True for better results

    per_device_train_batch_size: prompts per GPU per step.

    • Starting point: 2 (30B model on a single A100 80GB); drop to 1 if OOM
    • Compensate with gradient_accumulation_steps: effective_batch = batch_size × accum_steps
    • GRPO's actual workload is effective_batch × G — keep this product between 32 and 128

    warmup_ratio: fraction of total steps used for warmup.

    • Matters more in RL than in SFT: warmup uses a tiny LR so the policy "warms up" before any large gradient hits and damages the base model's abilities
    • Recommended: 0.05 to 0.1 (5–10% of total steps)

    kl_coef (KL coefficient): penalty strength for drifting away from the reference model.

    • Typical range: 0.001 to 0.1
    • Too small: the model may find reward-hacking strategies (gaming the reward with weird formats)
    • Too large: policy updates are over-constrained and learning is slow
    • Starting point: 0.01; watch the KL value and keep it in roughly 0.1–1.0

    10. OOM Debugging

    Out-of-memory is the most common problem when training models in the 30B class. A systematic OOM debug process beats randomly lowering parameters. Here's the routine I settled on.

    Step 1: locate which phase the OOM happens in

    • Data loading: rare. Usually a sequence is too long during tokenization. Check max_seq_length.
    • Forward pass: model parameters + activations exceed memory. Symptom: OOM on the first training step.
    • Backward pass: gradients + activations exceed memory. Symptom: forward passes succeed, backward OOMs.
    • Optimizer step: optimizer state suddenly loaded. Symptom: OOM after a few steps. Paged optimizer helps.
    • GRPO generation: G × batch_size sequences generated at once. Symptom: OOM before the reward calculation.

    Step 2: try these mitigations in order

    1. Drop batch size to 1: the most direct memory cut. Use gradient_accumulation_steps to keep effective batch.
    2. Enable gradient_checkpointing: turn it on if it isn't already. Required for 30B models. Cuts activation memory by 8–10×.
    3. Shorten max_seq_length: attention KV cache grows quadratically with sequence length (linearly after Flash Attention, but the constant is still large). Look at the actual maximum length in your dataset and set a reasonable cap.
    4. Switch to the paged optimizer: optim="paged_adamw_32bit", offloads optimizer state to CPU and reduces GPU memory peaks.
    5. Lower num_generations (G): from 8 to 4, halving the GRPO generation memory. Gradient quality drops but is usually fine.
    6. Lower LoRA rank r: from 8 to 4, halving trainable parameters. Small effect on training memory, larger effect on capacity.
    7. Use unsloth: if the above isn't enough, switch — its custom kernels use less memory at the same compute load.
    8. Multi-GPU distributed training: use DeepSpeed ZeRO-3 to shard parameters, gradients, and optimizer state across GPUs. Verify GRPO/ZeRO-3 compatibility before relying on it.

    Memory estimation (for diagnosis):

    Component Estimate Example (30B NF4)
    Base model (4-bit) params × 0.5 bytes 30B × 0.5 = 15 GB
    LoRA parameters (bf16) trainable_params × 2 bytes 42M × 2 = 84 MB
    Activations (with gradient checkpointing) batch × seq_len × hidden × layers × 2 bytes / 8 2 × 2048 × 7168 × 80 × 2 / 8 ≈ 7 GB
    Optimizer state (Adam) trainable_params × 2 × 4 bytes 42M × 8 = 336 MB
    GRPO generation cache G × batch × seq_len × hidden × 2 bytes 8 × 2 × 128 × 7168 × 2 ≈ 3 GB
    Total (estimate) ≈ 26 GB (fits on a single A100)

    These are approximate; actual usage is affected by PyTorch memory fragmentation, framework overhead, and so on, and is usually 10–20% higher than the estimate. Before committing to a long training run, measure peak usage on a single step with torch.cuda.max_memory_allocated().

    11. Evaluation and Analysis

    Why accuracy alone isn't enough: in our dataset, critical is 4% and informational is 30%. A dummy model that predicts informational for everything reaches 30% accuracy, but its critical recall is 0 — useless in production. For severely imbalanced classification, accuracy is misleading.

    What to look at instead:

    • Per-class precision / recall / F1: report each severity level separately so you know where the model is weakest.
    • Critical recall: the headline business metric. Target: at least 95% in production (no more than 5 misses per 100 real critical alerts).
    • Confusion matrix: visualize where the model gets confused (e.g., it often predicts medium when high is correct).
    • Reward curves during training: reward/mean should rise and stabilize; reward/std should stay non-zero (the group still has some diversity).
    • Generation parse rate: fraction of extract_severity returning "unknown" — measures how reliable the output format is.
    from sklearn.metrics import classification_report, confusion_matrix
import numpy as np

LABEL_LIST = ["critical", "high", "medium", "low", "informational"]

def evaluate_model(model, tokenizer, eval_dataset, label_list=LABEL_LIST):
    """
    Comprehensive evaluation for the alert severity classification model.
    Returns per-class metrics and highlights the critical recall.
    """
    model.eval()
    predictions = []
    true_labels  = []
    parse_failures = 0

    with torch.no_grad():
        for sample in eval_dataset:
            input_ids = tokenizer(
                sample["prompt"],
                return_tensors="pt",
                truncation=True,
                max_length=1024,
            ).input_ids.cuda()

            output_ids = model.generate(
                input_ids,
                max_new_tokens=64,
                temperature=0.1,        # low temp for deterministic eval
                do_sample=False,        # greedy decoding for reproducibility
            )

            # Decode only the new tokens (not the prompt)
            new_tokens = output_ids[0, input_ids.shape[1]:]
            response = tokenizer.decode(new_tokens, skip_special_tokens=True)

            pred = extract_severity(response)
            if pred == "unknown":
                parse_failures += 1
                pred = "informational"  # conservative fallback for eval

            predictions.append(pred)
            true_labels.append(sample["label"])

    # ── Per-class report ───────────────────────────────────────────────────────
    print("=" * 60)
    print("Per-class Classification Report")
    print("=" * 60)
    print(classification_report(true_labels, predictions, labels=label_list,
                                 digits=3, zero_division=0))

    # ── Confusion matrix ───────────────────────────────────────────────────────
    print("Confusion Matrix (rows=true, cols=predicted):")
    cm = confusion_matrix(true_labels, predictions, labels=label_list)
    print("Labels:", label_list)
    print(cm)

    # ── Most important: critical recall ───────────────────────────────────────
    critical_idx = label_list.index("critical")
    critical_row = cm[critical_idx]
    critical_recall = critical_row[critical_idx] / critical_row.sum() if critical_row.sum() > 0 else 0.0
    critical_false_neg_to_medium_plus = (
        sum(critical_row[label_list.index(l)]
            for l in ["medium", "low", "informational"])
    )

    print("\n" + "=" * 60)
    print("Business-Critical Metrics")
    print("=" * 60)
    print(f"Critical alert recall:        {critical_recall:.3f}  (target: >= 0.95)")
    print(f"Critical → medium/low/info:   {critical_false_neg_to_medium_plus}  (dangerous misses)")
    print(f"Parse failure rate:           {parse_failures / len(predictions):.3f}")

    # ── Severity-weighted error analysis ─────────────────────────────────────
    total_errors = 0
    dangerous_errors = 0  # underestimates by 2+ severity levels
    for i, true_l in enumerate(label_list):
        for j, pred_l in enumerate(label_list):
            if i != j and cm[i, j] > 0:
                true_rank = SEVERITY_RANK[true_l]
                pred_rank = SEVERITY_RANK[pred_l]
                if true_rank - pred_rank >= 2:  # dangerous underestimate
                    dangerous_errors += cm[i, j]
                total_errors += cm[i, j]

    print(f"Dangerous underestimates:     {dangerous_errors} / {total_errors} errors "
          f"({dangerous_errors/total_errors*100:.1f}% of all errors)" if total_errors > 0
          else "Dangerous underestimates:     0")

    return {
        "critical_recall": critical_recall,
        "parse_failure_rate": parse_failures / len(predictions),
        "confusion_matrix": cm,
    }

    Diagnosing abnormal training curves:

    • Reward hits a ceiling and stops growing: possibly reward hacking — the model has found a simple rule that locks in a high reward (e.g., always predict "high"). Check whether reward/std drops toward zero and whether the per-class prediction distribution is heavily skewed.
    • Reward oscillates without converging: learning_rate too large or kl_coef too small. Try halving learning_rate first.
    • Reward collapses early in training: not enough warmup, or learning_rate too high causing aggressive early updates. Raise warmup_ratio to 0.15.
    • Validation critical recall low while training reward is high: overfitting or distribution shift. Check whether the training set has enough diverse critical samples; consider data augmentation.

    12. Findings

    Conclusions worth carrying over to similar projects, distilled from the Chaitin Tech project.

    Finding one: reward function design beats base model choice

    The headline result. Switching to an asymmetric reward (heavy penalty for missing severe alerts) compared with a symmetric reward (right vs. wrong, equal cost) raised critical-alert recall by about 15 percentage points (from ~0.72 to ~0.87). Swapping base models at the same scale (Qwen3-30B-A3B vs. comparable peers) moved the same metric by about 3pp. Takeaway: when the business objective is well-defined, the quality of the training signal matters more than the model itself. "Use a better model" is tempting but inefficient; "use a more accurate reward" is high-leverage.

    Finding two: GRPO trained stably

    With lr=5e-6, kl_coef=0.01, G=8, GRPO converged within 3 epochs — the reward curve rose monotonically and then plateaued, no reward collapse and no severe oscillation. By contrast, when I tried PPO early on, the Value network's instability led the run to diverge after about 200 steps. GRPO's no-Critic design showed real stability advantages on this task.

    Finding three: QLoRA precision loss is negligible here

    Comparing QLoRA (4-bit NF4) to fp16 LoRA at the same training configuration: weighted F1 differed by less than 1pp (0.86 vs. 0.87), and critical recall by about 0.5pp. 4-bit quantization has minimal effect on classification, while the memory savings (60 GB → 15 GB) are real. Consistent with the original Dettmers et al. paper, but now with a task-specific data point.

    Finding four: explicit output-format constraints matter

    Adding "Respond with exactly one word: critical, high, medium, low, or informational." at the end of the prompt raised the parse rate from ~73% to ~97%. Without it, ~27% of outputs couldn't be parsed reliably; those samples received the -1.0 format penalty and added a lot of noise to the training signal. Constraining output format is the cheapest way to lift parse rate.

    Finding five: G=8 was the sweet spot for group size

    I systematically tested G=4, 8, 16:

    • G=4: noisier gradient estimate, needed about one extra epoch to match G=8, but each step is cheaper — useful when memory is very tight.
    • G=8: best balance. Memory utilization ~75% with batch_size=2 on 2× A100, and the trade-off between training speed and gradient quality landed well.
    • G=16: critical recall improved by about 1pp over G=8, but batch_size had to drop to 1 and the total run time went up. Marginal gain wasn't worth the marginal cost.

    Finding six: a two-phase training strategy worked

    The final approach was two-phase: phase 1 ran SFT on labeled data for 1 epoch as initial alignment (so the model first learned the right output format and rough classification direction); phase 2 ran GRPO for reward alignment. Compared with starting GRPO directly from the base model, the SFT warmup made GRPO converge about 30% faster and more stably early on, since the initial policy could already produce well-formatted classifications and the reward signal was higher quality.

    Summary: priority order for similar projects

    1. Get the reward function right first (asymmetric cost, defensive parsing, calibrated magnitudes)
    2. Use a structured output prompt to keep the parse rate high
    3. Warm up with SFT, then switch to GRPO
    4. Start at G=8, lr=5e-6 — don't burn time on hyperparameters too early
    5. Track critical recall as the headline metric, not overall accuracy/F1
    6. Only after all of the above, consider a larger base model
